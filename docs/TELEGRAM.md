# Telegram bot

`Mizan.Telegram` lets linked users log meals, check totals, and record weight. It calls the main API through `MizanApiClient` with internal service authentication (`X-Api-Key` and `X-Impersonate-User`); it has no direct database access or separate AI provider.

## Link an account

1. Open `/profile/settings/telegram` in the app and request a code.
2. Follow the generated `t.me/<bot>?start=<code>` link. Codes are single-use and expire after five minutes.
3. Telegram sends `/start <code>`; the bot resolves it through `/api/Telegram/resolve` and links the Telegram user to the signed-in Mizan account.

Unlinked chats receive a settings-page link. `/unlink` removes the connection without deleting logged data.

The bot is a Pro feature. Issuing a link code answers 402 for a Free account. A linked account that returns to Free keeps its link: the bot replies with the upgrade page and still accepts `/unlink` and `/help`, and it works again as soon as the account is Pro. `/api/Telegram/resolve` reports `isPro` for this.

## Commands

| Input | Behavior |
| --- | --- |
| `/today` | Daily totals against the user's targets |
| `/weight 82.4` | Records a weigh-in |
| `/plan`, `/plan tomorrow`, `/plan 2026-10-23` | The active plan's day: entries per slot with ✓ on logged ones, totals against the plan's rules, violations, the eating window. One **Log** button per unlogged recipe or food entry, a **Tomorrow** button, and **Open** to `{MiniAppUrl}/plan?planId=...&day=...`. No active plan points at `/meal-plan`. |
| `/shop` | The newest shopping list: up to ten unticked items grouped by prep session, with amounts and a "needs review" marker, "N left of M" at the end. One toggle button per item, **More** and **Back** to page, and **Open** to `{MiniAppUrl}/shopping-list?listId=...`. No list points at `/meal-plan`. |
| `/planme high protein, cheap` | Drafts a week from tomorrow with the assistant and replies with its summary, weekly cost and violations, and **Confirm** / **Discard** |
| `/notifications`, `/notifications on`, `/notifications off` | Says whether notifications come to this chat, with one **Turn on** or **Turn off** button (`nt:on`, `nt:off`), or sets it. See [notifications in Telegram](#notifications-in-telegram). |
| `/unlink` | Disconnects this chat |
| `/help` | Lists commands |
| A photo | Proposes nutrition with **Log it**, **Split**, and **Discard** actions |
| Other text | Continues the shared AI chat used on the website |

The plan and shopping cards carry one id per button, because two guids do not fit in 64 bytes: **Log** is `pe:{entryId}`, **Tomorrow** is `pd:{yyyy-MM-dd}`, a shopping toggle is `sh:{itemId}`, and **More** or **Back** is `sp:{page}`. The bot reads the rest back from the API when the button is pressed. A **Log** press finds its plan by reading today's and tomorrow's day (`GET /api/MealPlans/day`), the days a card is sent for, then calls `POST /api/MealPlans/{planId}/entries/{entryId}/log` with an empty body and renders the day again; an entry it cannot find is answered with "That card is too old to use". A toggle re-resolves the newest list, notes which page the item sat on, calls `PATCH /api/ShoppingLists/items/{itemId}/toggle` with `{ "isChecked": true }`, reads the list again and renders that page. Without a date, `GET /api/MealPlans/day` dates the day in the user's time zone; `/plan tomorrow` adds a day to that date, and only when no plan covers today does the bot fall back to UTC, because neither the resolve call nor `/api/Users/me` exposes the time zone to a service caller.

**Log it** logs the combined nutrition totals. **Split** asks how many people share the meal (2 to 5) and sends the whole totals with `sharedBetween` on `POST /api/Meals`; the API divides them (calories to whole numbers, grams to a tenth) and names the entry "(1/N share)", so the bot computes nothing. Each button carries the meal's totals, because the bot keeps no state, so a button works whenever it is pressed. The meal name is cut by UTF-8 bytes to keep every button under Telegram's 64-byte limit. The card has no inline quantity editor. Shared API consent, entitlements, validation, and AI quotas apply.

## Mini App

The Mini App is the web app opened inside Telegram's WebView: Next.js serves `/tg` (the home), `/tg/log`, `/tg/plan` and `/tg/shopping-list` without the shell, and `web_app` buttons in the chat open them. `MiniAppPages` (`Mizan.Contracts/Telegram`) lists these pages; every button the bot sends points at one of them, and a test holds it to that. At startup the bot sets the chat's menu button (`setChatMenuButton`) to a `web_app` **Open Mizan** button for the home when the Mini App URL is HTTPS, and back to the commands menu otherwise. The `/start` greeting after linking and `/help` carry the same **Open Mizan** button, and the `/plan` and `/shop` cards end with an **Open** button to the day or list they show, each in a row of its own. To make Mizan the bot's main Mini App in Telegram's profile and search as well, register the same URL in BotFather (`/mybots`, Bot Settings, Configure Mini App). Telegram hands the page a signed `initData` string naming the Telegram user and the moment it was opened. The page turns it into an ordinary Mizan session in one call, and the bot token never leaves the bot service:

1. The page sends `POST /telegram/miniapp/session` to the bot service with `{ "initData": window.Telegram.WebApp.initData }`. The route lives on the app's public host next to `/telegram/webhook`.
2. The bot verifies the signature (`TelegramInitData`): the data-check string is every field but `hash`, sorted by key and joined with newlines; the key is HMAC-SHA256(`WebAppData`, bot token); the hash comparison is constant-time. It refuses an `auth_date` older than five minutes (`TelegramBot__MiniAppMaxAge`) or more than a minute in the future, a repeated field, and a `user` field it cannot read.
3. The bot calls `POST /api/Telegram/sessions` with its service key and `{ telegramUserId, ipAddress, userAgent }`. The API finds the linked account, applies the sign-in checks a password login makes (locked, banned, unverified), applies the same Pro gate as the rest of the bot, creates an ordinary `user_sessions` row with a 24-hour sliding life (`Telegram__MiniAppSessionLifetime`), audits the command, and returns `{ token, expiresAt, userId }`.
4. The bot answers `200 { token, expiresAt }` and sets `mizan_session=<token>; Path=/; HttpOnly; Secure; SameSite=Lax; Expires=<expiresAt>` (no `Secure` in Development), the same attributes as the API's own sign-in cookie. The page is signed in at once; `GET /api/Auth/me` and every other call carry the cookie.

In the web app (`frontend/app/tg`), the layout drops the navigation and footer, loads `telegram-web-app.js` with `next/script`, calls `WebApp.ready()` and `expand()`, and maps Telegram's `--tg-theme-*` colours onto the app's tokens where Telegram sends them. `useMiniAppSession` (`lib/tg`) posts `initData` once per opening and resolves to `signed_in` or a refusal; an empty `initData` (a page opened outside Telegram) is `not_in_telegram` and calls nothing. Only then do the pages fetch with `clientApi` and render `PlanDetail` (with **Log**) or `ShoppingListView` (with ticks). Without `planId`, `/tg/plan` reads `GET /api/MealPlans/day`; without `listId`, `/tg/shopping-list` opens the newest list, and with no list at all it says "No shopping list yet." with a link to the lists. The home (`MiniAppHome`) shows only what the API returns: today's totals from `GET /api/Meals` against the goal's calories, the first unlogged entry of today's plan with **Log**, and rows for **Log a meal** (`/tg/log`, the web's meal form), **Today's plan** and **Shopping list**; a part that fails or has nothing is left off. Every link stays inside `/tg`, the full app opens through **Open in browser** (`WebApp.openLink`), and any other `/tg` path renders `app/tg/not-found.tsx`: one sentence and **Back to today**. Each page's primary action is also on Telegram's main button, through `mainButton()` (`lib/tg/webApp.ts`) and `useMainButton` (`lib/tg/useMainButton.ts`): **Log a meal** on `/tg`, **Make shopping list** on `/tg/plan` while the plan has entries, and **Clear checked** on `/tg/shopping-list` while an item is ticked and the person may edit the list. The button shows Telegram's progress spinner while the write runs and is hidden when the page has no such action or is left. The in-page buttons stay, so the page also works where the main button is missing. A refusal shows one sentence and one action: `not_linked` opens `linkUrl` and `upgrade_required` opens `upgradeUrl` with `WebApp.openLink`; the others show the bot's message. `proxy.ts` never sends `/tg` or `/telegram` to `/login`, and `/tg` pages answer with `frame-ancestors 'self' https://web.telegram.org` instead of `X-Frame-Options: DENY`, because Telegram Web shows a Mini App in an iframe.

The route handler `app/telegram/miniapp/session/route.ts` forwards the body, `User-Agent`, and `X-Forwarded-For` to `${TELEGRAM_BOT_URL}/telegram/miniapp/session` (server-side; Compose defaults it to `http://telegram:5002`) and relays the status, the JSON body, and `Set-Cookie` unchanged. It never logs `initData`. The session's `ipAddress` is the browser's address only when the hop in front of the bot is trusted (`TelegramBot__TrustedProxies`, see [Configure and run](#configure-and-run)); otherwise it is the address that connected. Where the reverse proxy routes the path to the bot, as in production, the handler is not reached.

Refusals from the bot endpoint: `400 bad_request` (no `{ initData }` body), `401 invalid_init_data` (bad signature, stale, malformed), `404 not_linked` with `linkUrl` (the Telegram settings page), `402 upgrade_required` with `upgradeUrl`, `403 forbidden` or `429 account_locked` with the API's reason, and `502 api_unavailable`. The API endpoint itself answers `404 not_found`, `402 upgrade_required`, `403 forbidden` (banned) or `email_not_verified`, and `429 account_locked`. The frontend must call the bot endpoint on open, read the status, and show the link page on `not_linked`; it never sees or handles the bot token, and `Authorization: Bearer` is not a way to present a user session.

## Notifications in Telegram

A person can receive their Mizan notifications in the linked chat as well as in the app. It is opt-in and off by default: linking the bot alone sends nothing. The switch is `notifyByTelegram` on `GET` and `PUT /api/Users/me`, and every surface uses that endpoint: **Send notifications to Telegram** on `/profile/settings/telegram`, `/notifications on` and `/notifications off` in the chat, and the MCP `update_my_profile` tool. The API refuses to turn it on without a linked chat (400), and unlinking from either side, or linking the chat to another account, turns it off.

`NotificationWriter` is the one place a notification fans out: the row, a push job, and, when the switch is on, a `telegram-message` outbox job keyed `telegram:notification:{notificationId}`. The messenger still sends nothing unless the bot service is configured, the chat is linked and the account is Pro. The message is the title, then the body on the next line. A notification that links to a plan (`/meal-plan/{id}`) or a shopping list (`/shopping-lists/{id}`) gets an **Open** button to `{MiniAppUrl}/plan?planId=...` or `{MiniAppUrl}/shopping-list?listId=...` (`MiniAppPaths`, Application); any other link is sent as plain text.

## Evening reminder

A person with an active plan whose rules set `EatingWindowEnd` gets one reminder per plan day, 30 minutes before the window closes in their time zone: "Your window closes at 20:00. Today: 1,640 of 1,800 kcal." Today's calories are the diary's total for that plan day; the target is the plan's `TargetCalories`, and without one the line ends at "Today: 1,640 kcal." A household plan reminds every member who follows it that day, each in their own time zone and with their own diary. A member follows the plan `GET /api/MealPlans/day` shows them: their own personal plan comes first, so a member whose own plan covers the day gets only that plan's reminder, or none when it has no window. It arrives as an in-app notification (type `evening_reminder`, linking to `/meal-plan/{planId}?day=` for that plan day), as a push where a phone is registered, and in Telegram only when the person has [turned on notifications in Telegram](#notifications-in-telegram), with an **Open** button to the plan day.

- `EveningReminderScheduler` scans every 15 minutes and queues the next reminder of each person who follows a plan (its owner and each household member) that falls within two hours as an `evening-reminder` outbox job, keyed `evening-reminder:{userId}:{day}:{HHmm}`. A repeat scan finds the same key and adds nothing; a moved window gets a new key.
- When the job runs, `EveningReminders` checks it again with `EveningReminderSchedule` (Application): the person still follows an active plan with a window on that day (the reminder names the plan they follow when it is sent), the window has not closed, the job is still the next reminder, and no reminder went out on that local calendar day. The last one sent is read from the notifications table. A window ending before 00:30 is reminded about late the evening before. The text is `EveningReminderText` (Domain).
- The API never holds the bot token. A `telegram-message` outbox job calls the bot service's `POST /internal/notify` with the service key in `X-Api-Key` and `{ telegramUserId, text, openPath }` (`TelegramNotifyRequest`). The bot escapes the text, adds the **Open** button when the Mini App is HTTPS, and answers 204, 401 for a wrong key, 400 for a bad body, or 502 when Telegram did not take it, which the outbox retries.

## Configure and run

The bot's environment holds only how it reaches the API and the public app: `TelegramBot__ApiUrl`, `TelegramBot__ServiceApiKey` (`MCP_SERVICE_KEY`), `TelegramBot__PublicUrl` (`PUBLIC_APP_URL`) and `TelegramBot__TrustedProxies`. Everything else is a runtime setting in **Admin → Settings → Telegram** ([runtime settings](ADMIN.md#runtime-settings)): `Telegram.BotToken`, `BotUsername` (which builds account-link URLs), `UseWebhook`, `WebhookSecret`, `MiniAppUrl`, `MiniAppMaxAgeSeconds`, `MiniAppSessionHours` and `BotServiceUrl`. The old `TelegramBot__BotToken`, `UseWebhook`, `WebhookSecret`, `MiniAppUrl` and `MiniAppMaxAge` variables are ignored with a warning at startup.

The bot reads its settings from `GET /api/internal/settings/telegram-bot` with the service key: at startup (retrying from 1 s up to a minute until the API answers), every five minutes, and at once when the API calls its `POST /internal/settings-changed` after an administrator changes a `Telegram.*` key. Until the first answer it has no token and stays idle; `GET /health` reports `settingsLoaded`. When the token, the webhook switch or the secret change, it brings Telegram in line without a restart: it registers the webhook with the new secret, or removes it and starts polling, and sets the command list and menu button again. Anyone holding the service key can read the token through that route, so the key stays on the internal network. `Telegram.MiniAppUrl` is optional and defaults to `{PublicUrl}/tg`; Telegram accepts `web_app` buttons over HTTPS only, so the bot leaves every `web_app` button out when the URL is plain HTTP, as in local development.

`TELEGRAM_TRUSTED_PROXIES` (`TelegramBot__TrustedProxies`) lists the IP addresses or CIDR ranges, comma-separated, whose `X-Forwarded-For` the bot believes. ASP.NET's forwarded headers middleware reads the header from the right, past every trusted hop, and stops at the first address that is not one, so a header sent from anywhere else, or a forged entry to the left of the proxy's, is ignored. Empty trusts loopback only. Development Compose defaults to `172.16.0.0/12`, Docker's default bridge range, where the frontend container sits; a request from the host to the published port 5002 also arrives from that range, which is acceptable only in development. In production set it to the subnet of `proxy-net`, which nginx and the frontend share (`docker network inspect proxy-net --format '{{(index .IPAM.Config 0).Subnet}}'`); left empty, sessions record nginx's address. An entry that is neither an address nor a range stops the bot at startup.

The API reaches the bot at `Telegram.BotServiceUrl` to send notifications to Telegram and to signal a settings change; empty, notifications stay in the app and the bot notices a change within five minutes. Set it to `http://telegram:5002` in development and `http://mizan-telegram:5002` in production. Do not route `/internal/notify` or `/internal/settings-changed` through the reverse proxy.

The production Compose file enables the optional bot with `COMPOSE_PROFILES=telegram`. It uses `Mcp__ServiceApiKey` for internal API authentication in both directions: the bot sends it to the API as `TelegramBot__ServiceApiKey`, and the API sends the same key to the bot's `/internal/notify`. Never give the bot the admin service key: the API's notify calls would then be refused with 401. The regular key acts for an administrator as an ordinary user, so admin accounts use the bot like anyone else and no admin endpoint is reachable through it ([architecture](ARCHITECTURE.md#identity)). When the API will not act for the account (401), the bot says so and points at sign-in and the Telegram settings page rather than answering "Unauthorized". It also uses `App__PublicUrl` (falling back to `PUBLIC_APP_URL`) for public links. The API stores the token and webhook secret encrypted and hands them only to the bot service. The image build workflow includes Telegram, and a manual run builds only that image from the default branch.

`Telegram.UseWebhook=false` (the default) selects long polling without a public hostname or TLS. Switching to it removes any previous webhook before polling. Commands are registered automatically in either mode.

For production webhooks:

- Set `Telegram.UseWebhook` to true and `Telegram.WebhookSecret` to a random value (for example, `openssl rand -hex 32`). Rotating the secret later takes effect at once: the bot registers the webhook with the new one, and an update carrying the old one is refused.
- Make `PUBLIC_APP_URL` publicly reachable over HTTPS.
- Route `/telegram/webhook` and `/telegram/miniapp/session` to the Telegram container on the app's public host. See [request boundaries](ARCHITECTURE.md#request-boundaries).

`WebhookRegistrar` registers `{PublicUrl}/telegram/webhook` and polling stays off. Startup does not wait for it. Registration counts only when Telegram answers `ok: true`; a refusal (an unresolvable new hostname, a `secret_token` outside `A-Z a-z 0-9 _ -`, an untrusted certificate, a port other than 443, 80, 88 or 8443) is logged with Telegram's `description` and retried after 5 s, doubling to 5 min, until Telegram accepts it. Success is logged once, after which the bot compares `getWebhookInfo`'s URL with its own and logs Telegram's `last_error_message` if it reports delivery errors. A missing webhook secret prevents registration and reports `failed`. Requests must present the matching `X-Telegram-Bot-Api-Secret-Token`; comparison is constant-time and invalid requests receive 404. Updates are acknowledged immediately and processed in the background. A redeploy or a settings change requests webhook registration again.

`GET /health` on the service returns `{ status, configured, mode, webhook }`, with mode `webhook` or `long-poll` and `webhook` as `{ state, lastError, attempts }`: `disabled` in long-poll mode, then `pending`, `registered`, or `failed` with Telegram's last reason. A deaf bot shows as `failed` there while the service stays healthy.

## Conversation and photos

Chat replays the last ten turns and a rolling summary stored on the shared thread. Summary refresh happens after a saved reply; a failed refresh preserves the previous summary without failing the turn. The reply ends with one line per performed action (`✓` or `✗` with the error), so a request to create a list shows that it happened.

The bot reads and writes the records in `Mizan.Contracts` (`LogMealRequest`, `DailyNutritionTotals`, `FoodAnalysisResult`, `AiChatTurnDto`) and formats `/today` with `Mizan.Domain.Nutrition.NutritionText`, the same wording the assistant's tools and context use.

`/planme` sends the words as the preference to `POST /api/MealPlans/generate` and spends the planning allowance. **Confirm** (`pm:ok:{planId}`) accepts the draft and **Discard** (`pm:no:{planId}`) declines it; the handler is `Bot/PlanMeHandler.cs`.

Photo analysis uses `/api/Nutrition/ai/analyze-image` and stores the image under `meals/` in object storage. A storage failure loses the retained picture but does not discard the analysis. See [AI](AI.md) for consent and metering.

## Verify

Backend integration tests cover account linking, the Mini App session endpoint, notifications in Telegram and the evening reminder through the outbox, service authentication, and shared API behavior. The bot's commands, `/notifications` among them, are tested through the fake HTTP world. `TelegramInitData` has unit tests over a fixture signed with a known fake token, and the bot's Mini App endpoint is tested through the fake HTTP world. Verify a configured bot separately in its selected mode, including linking, a read, a confirmed write, and opening the Mini App from the `/help` button. Browser fixture tests do not contact Telegram: `e2e/tg.spec.ts` injects a fake `window.Telegram.WebApp` with a main button it can press, answers the script URL with nothing, and `e2e/fixture-tg.ts` plays the bot endpoint with one outcome per opening. `e2e/telegram-settings.spec.ts` covers the notifications switch.
